OWASP Top 10 Deep Dive: A01 — Broken Access Control

Broken Access Control has held the #1 spot on the OWASP Top 10 since 2021, present in 94% of tested applications. This breakdown covers how it manifests, how to find it, and how to exploit it in a lab setting — plus what actually fixes it.

01 — What is Broken Access Control?

Access control enforces a policy so that users cannot act outside their intended permissions. When that enforcement fails — whether due to missing checks, client-side-only controls, or insecure direct references — you get Broken Access Control (BAC).

It's the most widespread web vulnerability class because it's easy to introduce and hard to catch with automated scanning alone. Unlike SQL injection which has a clear signature, BAC requires business logic context: you need to understand what a user should be allowed to do before you can determine whether they can exceed it.

02 — IDOR: Insecure Direct Object Reference

IDOR is the most common and immediately impactful subtype. It happens when an application uses a user-controlled identifier (like an ID in a URL or request body) to access data directly, without verifying that the requesting user owns or is permitted to access that object.

Classic Example

A user views their own order details at:

GET /api/orders/10482 Authorization: Bearer eyJhbGciOiJIUzI1NiJ9... {"id": 10482, "user": "alice", "total": "$42.00", ...}

The application trusts the ID parameter without checking ownership. Simply changing the ID reveals another user's order:

GET /api/orders/10481 Authorization: Bearer eyJhbGciOiJIUzI1NiJ9... {"id": 10481, "user": "bob", "email": "bob@example.com", "total": "$89.00", ...} # Full PII of another user returned — no error, no auth check
// testing approach

Create two accounts. Perform an action with account A, capture the request ID, then replay it authenticated as account B. If B gets A's data — it's IDOR. Burp's Repeater makes this trivial.

IDOR Isn't Just URLs

IDORs appear in many places beyond URL parameters:

  • POST body — {"account_id": 9001, "action": "download_statement"}
  • Hidden form fields — <input type="hidden" name="user_id" value="42">
  • Cookies — some apps store object IDs in cookies without signing them
  • GraphQL — direct node ID queries: node(id: "VXNlcjoxMjM=")

03 — Privilege Escalation (Vertical)

Vertical privilege escalation means a lower-privileged user accessing functionality reserved for higher-privileged roles — typically user → admin.

Admin Panel via Direct URL

# Logged in as a regular user, navigate directly to: GET /admin/users GET /admin/settings GET /admin/delete?user=alice # If the server only hides these links from the UI # but doesn't enforce the check server-side — full admin access

Parameter Manipulation

POST /api/user/update Content-Type: application/json # Original request: {"username": "alice", "email": "alice@example.com"} # Modified — adding a role field not shown in the UI: {"username": "alice", "email": "alice@example.com", "role": "admin"} # Server accepts mass assignment → alice is now admin
// mass assignment

This is a specific BAC variant called Mass Assignment (or auto-binding). Frameworks like Rails, Laravel, and Spring can automatically bind request parameters to model properties. If sensitive fields like role or is_admin aren't explicitly excluded, they become exploitable.

04 — Force Browsing & Missing Function-Level Control

Some endpoints are "protected" only by not being linked from the UI. An attacker who knows (or guesses) the URL can access them directly.

# Wordlist-based discovery of unlinked admin endpoints gobuster dir -u https://target.com -w /usr/share/seclists/Discovery/Web-Content/common.txt /admin [200] /admin/backup [200] /api/v1/admin [200] /debug [200] ← environment variables, DB credentials

05 — Finding BAC with Burp Suite

The Two-Account Method

  1. Open Burp Suite, set up two browser profiles (one per account)
  2. In browser 1 (victim), perform all available actions — Burp captures every request
  3. In browser 2 (attacker), copy the victim's requests into Repeater but use the attacker's session cookie
  4. Send each request and observe if the server enforces authorization

Burp's Autorize Extension

Autorize automates the two-account method. Configure it with the low-privileged session token and it automatically re-sends every captured request with that token, flagging any that return a 200 instead of 401/403.

# Autorize intercept filter — configure to re-send with: Cookie: session=LOW_PRIV_SESSION_TOKEN # Results table shows three columns: # Original response | Low-priv response | Status GET /admin/users 200 OK → 200 OK → BYPASSED ⚠ GET /api/profile 200 OK → 401 Unauth → Enforced ✓

07 — Remediation

Access control is a server-side concern — never rely on hiding UI elements or client-side validation alone. Concrete fixes:

Enforce Ownership Checks

# ❌ Vulnerable — trusts the ID in the request def get_order(order_id): return db.query("SELECT * FROM orders WHERE id = ?", order_id) # ✅ Fixed — ties the query to the authenticated user's ID def get_order(order_id, current_user): order = db.query("SELECT * FROM orders WHERE id = ? AND user_id = ?", order_id, current_user.id) if not order: raise AuthorizationError("Access denied") return order

Use Indirect References

Instead of exposing database IDs, map them to per-session opaque tokens. A user's session maps token_abc → order_10482 server-side — even if they guess another token, it won't map to anything in their session.

Centralize Authorization

Don't scatter access checks across controller methods. Use a middleware or policy layer that enforces rules consistently — frameworks like Pundit (Rails), Spring Security, and Laravel Gates provide this pattern.

// key takeaway

The root cause of Broken Access Control is almost always "we check this in some places but not all places." Centralizing authorization logic eliminates the inconsistency that attackers exploit.
